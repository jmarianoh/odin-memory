# 30.07 — Exportación por el diario, `cloud upgrade` y atestación de origen

Spec 0.29.0 (F9.2c-2, F9.4 parcial). Tres piezas del cliente de la nube: el modo nube del `Syncer` (la exportación respaldada por el diario de mutaciones), la migración de un proyecto con `odin cloud upgrade …` y la atestación humana del origen de un prompt con `odin cloud attest-prompt-source`. Además aporta los archivos de Docker del servidor.

## Modo nube del `Syncer`

`new Syncer(store, { transport, project, targetKey, cloudMode: true, log })`. Con `cloudMode` falso (Git y pruebas) nada cambia. Con él, `export(createdBy, project)`:

1. **Comprobación previa** (`#ensureCloudPreflight`): sin proyecto (ni en la llamada ni en el `Syncer`) → `cloud sync requires an explicit --project scope; --all is not supported in cloud mode`; proyecto sin inscribir → se anota `markSyncBlocked(targetKey, 'blocked_unenrolled', mensaje)` y se lanza `cloud sync blocked_unenrolled: project "<p>" is not enrolled for cloud sync`.
2. Lee manifiesto, chunks conocidos y los datos del proyecto (`exportProject`) **sin** el filtro de alcance `project` de las observaciones (las personales también viajan a la nube).
3. **Chunk respaldado por el diario** (`#filterByPendingMutations`, proyecto vacío → chunk vacío):
   - Rellena el diario de los proyectos inscritos (`ensureEnrolledProjectSyncMutations`) y lee todas las mutaciones pendientes del destino `cloud` en páginas de 5000 (`listPendingSyncMutationsAfterSeq`), error `pending mutation pagination did not advance …` si una página no avanza.
   - Una mutación de sesión sin proyecto cuya sesión local pertenece al proyecto → error `blank-project session mutation seq=N entity_key="k" requires cloud upgrade diagnosis and repair before export`.
   - Proyecto de una mutación (`resolveMutationProject`): el de la fila (canónico); si no, el de su carga (`project`, la carga puede ser una cadena JSON anidada); si no, el de la sesión local de `session_id`. Las de otro proyecto se descartan; las que no tienen ninguno solo se admiten si su entidad existe en los datos del proyecto; y una sesión sin proyecto que llega aquí → error `blank-project session mutation seq=N entity_key="k" has no authoritative local session in project "<p>"; run cloud upgrade doctor`.
   - El chunk lleva las observaciones y prompts de las mutaciones elegidas, las sesiones de las mutaciones de sesión y las que esas filas referencian, y `mutations` con las filas elegidas tal como las guarda el diario (`seq`, `target_key`, `entity`, `entity_key`, `op`, `payload`, `source`, `project`, `occurred_at`, `acked_at` si no es nulo, `disposition` y los campos de disposición no vacíos).
4. **Subida por tandas** (`splitCloudExportChunk(chunk, seqs, 4 MiB)`): las mutaciones conservan su orden y su alineación con `seqs`; el coste de añadir una mutación es `bytes(payload) + 128` más lo que aporte su entidad (observación o prompt, si no estaba en la tanda) y las sesiones que esa entidad necesita y la tanda aún no lleva; se abre una tanda nueva cuando la actual ya tiene mutaciones y se pasaría del tope (una mutación mayor que el tope viaja sola). Sin tope (`≤ 0`) o con `seqs` de otra longitud no se parte.
5. Por cada tanda: se serializa (`chunkToJson`), se canoniza para el proyecto (`canonicalizeForProject`, error `canonicalize cloud chunk: …`) y se calcula su id. Si el id ya era conocido solo se reconcilia el registro de chunks y se **acusan** las mutaciones de la tanda. Si no, se escribe el chunk (`write chunk: …`), se añade al manifiesto, se registra como sincronizado y solo entonces se acusan sus mutaciones (`ackSyncMutationSeqs`), de modo que una subida interrumpida se reanuda por la primera mutación sin acusar.
6. Resultado: `{ chunk_id, chunks_exported, sessions_exported (sesiones distintas), observations_exported, prompts_exported, mutations_exported, is_empty }`; sin chunks escritos, `is_empty: true`. Un chunk vacío con `seqs` acusa esas filas.

`odin sync --cloud` y `odin cloud upgrade` crean el `Syncer` con `cloudMode: true`.

## Migración de un proyecto (`src/store/cloud-upgrade.js`, `src/cli/commands/cloud-upgrade.js`)

Etapas guardadas en `cloud_upgrade_state` (`planned`, `doctor_ready`, `doctor_blocked`, `repair_applied`, `bootstrap_enrolled`, `bootstrap_pushed`, `bootstrap_verified`, `rolled_back`) con clase de reparación (`none`, `ready`, `repairable`, `blocked`, `policy`), código y mensaje del último problema y la **instantánea** `{captured, project_enrolled}` (JSON). Una etapa o clase desconocida se normaliza a `planned` / `none`.

### Estado

- `readUpgradeState(store, p)` → fila con la instantánea decodificada o `null`. `saveUpgradeState(store, estado)`: `INSERT … ON CONFLICT` que **no sustituye una instantánea ya capturada por otra sin capturar**; vacíos se guardan como NULL; proyecto vacío → `cloud upgrade project must not be empty`.
- `captureUpgradeSnapshot(store, p)`: proyecto vacío → `cloud upgrade bootstrap requires project`; si el estado está en `bootstrap_enrolled|pushed|verified` sin instantánea capturada → `bootstrap checkpoint requires a captured pre-bootstrap snapshot`; si ya hay una, la devuelve; si no, guarda `{captured: true, project_enrolled: <inscrito ahora>}` conservando el resto del estado.
- `canRollbackUpgrade`: hay instantánea y la etapa no es `bootstrap_verified`. `rollbackUpgrade`: errores `cloud upgrade rollback requires project`, `rollback requires existing upgrade checkpoint state`, `rollback requires a captured pre-bootstrap snapshot`, `rollback is unavailable post-bootstrap; use explicit disconnect/unenroll flows`; si no, inscribe o desinscribe según la instantánea, pone la etapa `rolled_back` y vacía error, hallazgos y acciones.

### Mutaciones heredadas

`diagnoseLegacyMutations(store, p)` → `{project, repairable_count, blocked_count, findings}` evaluando, en una transacción de lectura, las mutaciones **pendientes de salida** del proyecto (`target_key = 'cloud'`, `project = p`, sin acusar, `disposition = 'pending'`, por `seq`) más las **sesiones sin proyecto** (`project = ''`, `upsert`) que se le atribuyen: porque su sesión local es del proyecto o, si la sesión local no existe o no tiene dueño, porque su carga dice `project = p`.

Cada hallazgo: `{seq, entity, op, entity_key, target_key, project, repairable, reason_code, message, repair_hint?}`; `reason_code` es `upgrade_repairable_legacy_mutation_payload` (reparable) o `upgrade_blocked_legacy_mutation_manual` (bloqueado). Evaluación de una mutación (`evaluateMutation`):

1. Proyecto: vacío → solo una sesión `upsert` con clave y sesión local con dueño canónico no vacío es atribuible (dueño = ese proyecto); en otro caso bloqueada con `mutation project must be non-empty and canonical for cloud transport and cannot be inferred from authoritative local state`. Con proyecto recortado distinto del original → `mutation project must be canonical`.
2. Carga vacía → `legacy mutation payload is empty`. Entidad/op fuera de `session|observation|prompt` con `upsert|delete` y `relation` con `upsert` → `unsupported legacy mutation "<entidad>"/"<op>"`.
3. La carga debe ser un objeto JSON (`null` equivale a `{}`); otra cosa → `decode <entidad> payload: json: cannot unmarshal <array|string|number|bool> into Go value of type store.sync<Entidad>Payload` (un JSON ilegible: `decode <entidad> payload: <detalle>`).
4. **Sesión**: `id` recortado; si el proyecto de la mutación era vacío, la carga debe coincidir con el dueño local (`session payload project conflicts with local session project`) y se rellena; un `id` vacío toma la clave (`session payload id is required` si no hay); clave distinta del `id` → `session entity_key "k" does not match payload id "i"`; con proyecto vacío y directorio no vacío debe coincidir con el local (`session payload directory conflicts with local session directory`); un `upsert` cuya carga no trae la clave `ownership_mode` (ausente; una clave presente, aunque vacía, no se toca) hereda la propiedad de la sesión local si esta es `project_owned`: la carga debe coincidir con su dueño (`session payload project conflicts with local session project`), se le añade `ownership_mode = project_owned` y la mutación pasa a reparable; con `ownership_mode = project_owned` (propio o heredado) y un `directory` que no es texto —el `null` crudo no se toma por blanco— → `pulled session directory is invalid: directory must be a string` (una clave `directory` ausente es válida); un `upsert` sin directorio (y no `project_owned`) lo toma de la sesión local o, si no hay, `session payload directory is required and cannot be inferred from local state`. Se reescribe solo si algo cambió (reparable: `session payload is missing required fields`).
5. **Observación y prompt**: `sync_id` vacío toma la clave (`<entidad> payload sync_id is required`); clave ≠ `sync_id` → `<entidad> entity_key "k" does not match payload sync_id "i"`. En `upsert`: la observación rellena `session_id`, `type`, `title`, `content` y `scope` vacíos desde `observations` (por `sync_id`, incluidas las borradas); el prompt rellena `session_id` y `content` desde la última fila de `user_prompts` y `source_inbox_id` si falta; lo que siga vacío → `<entidad> payload missing required upsert fields: a, b, …` (orden `session_id, type, title, content, scope` / `session_id, content`).
6. **Relación**: igual con `sync_id`; los campos vacíos (`source_id`, `target_id`, `relation`, `judgment_status`, fechas; `reason`, `evidence`, `confidence`, `marked_by_model`, `session_id` si son nulos; `marked_by_actor`/`marked_by_kind` si están vacíos) se toman de la última fila de `memory_relations` con ese `sync_id`; `project` vacío toma el de la mutación; faltan → `relation payload missing required upsert fields: source_id, target_id, relation, judgment_status, marked_by_actor, marked_by_kind, project` (los que correspondan).

La carga reparada es la carga original con los campos rellenos (las claves originales se conservan; no se añaden los campos con valor cero que añadiría otra implementación).

### Reparación

`repairUpgrade(store, p, apply)` devuelve `{class, reason_code, message, planned_action?, applied}`:

1. Proyecto vacío → `blocked` / `upgrade_blocked_project_required` / `project is required for cloud upgrade repair`.
2. Si el estado de `cloud:<p>` tiene un motivo `auth_required`, `policy_forbidden` o `cloud_config_error` → clase `policy`, código `upgrade_policy_auth_required|upgrade_policy_forbidden|upgrade_policy_cloud_config_error`, mensaje `manual-action-required: <motivo guardado o "cloud policy/auth precondition must be resolved before repair">`.
3. Sin inscribir → `blocked` / `upgrade_blocked_manual` / `project "p" is not enrolled; run doctor/bootstrap guidance first`.
4. Con `apply` y hallazgos reparables, se reescriben en una transacción (`UPDATE sync_mutations SET payload, project … WHERE … AND acked_at IS NULL AND disposition = 'pending'`) todas las reparables, aunque haya bloqueadas.
5. Con bloqueadas: `blocked` / `upgrade_blocked_legacy_mutation_manual`, `applied` según se reparó, mensaje con la primera bloqueada (`manual-action-required: <mensaje> (seq=N entity=e entity_key="k" op=o)`), precedido de `applied R repairable payload(s); B remain blocked: ` (aplicado) o `R repairable payload(s) would apply; B would remain blocked: ` (simulacro con reparables).
6. Solo reparables: sin aplicar → `repairable` / `upgrade_repairable_legacy_mutation_payload` / `project "p" has R repairable legacy mutation payload issue(s)` / `planned_action: repair_legacy_mutation_payloads`; aplicadas → `applied deterministic legacy mutation payload repairs for project "p"` y etapa `repair_applied`.
7. Sin hallazgos: si faltan filas del diario (alguna sesión del proyecto con directorio no vacío (o `project_owned`) u observación viva sin fila `local` pendiente o en cuarentena) → `repairable` / `upgrade_repair_backfill_sync_journal` / `project "p" has deterministic local sync metadata gaps` / `planned_action: backfill_sync_journal` (con `apply`: `backfillProjectSyncMutations` en una transacción, etapa `repair_applied`, `applied: true`); si no → `ready` / `upgrade_repair_noop` / `project "p" has no deterministic local repairs to apply`.

`remirrorProject(store, p)`: proyecto vacío → `cloud remirror requires project`; sin inscribir → `cloud remirror requires enrolled project "p"`; reencola el estado actual con una fuente nueva `remirror:<nanosegundos>` (con sufijo `:N` si ya existía), sin tocar las filas anteriores.

### Órdenes (`odin cloud upgrade <orden> --project <p>`)

Sin orden: `usage: odin cloud upgrade <doctor|repair|bootstrap|remirror|status|rollback> --project <name>` en el error estándar (código 1). `--help|-h|help`: `odin cloud upgrade`, `workflow: doctor -> repair -> bootstrap -> status/rollback`, `recovery: use remirror only to rebuild cloud state from authoritative local data`, `cloud is opt-in replication/shared access; local SQLite remains source of truth` y la línea de uso. Orden desconocida (se compara en minúsculas): `unknown cloud upgrade command: x` / `supported cloud upgrade commands: doctor, repair, bootstrap, remirror, status, rollback`. `--project` (valor normalizado) falta → `usage: odin cloud upgrade <orden> --project <name>` (repair añade ` [--dry-run|--apply]`, bootstrap ` [--resume]`) y `error: --project is required`.

- **doctor**: nube configurada = URL válida; política denegada = motivo `policy_forbidden` en el estado de `cloud:<p>`. Diagnóstico base: política → `blocked/policy/policy_forbidden/project "p" is blocked by organization policy`; sin nube → `blocked/policy/cloud_config_error/cloud configuration is required before upgrade bootstrap`; sin inscribir → `blocked/repairable/upgrade_repairable_unenrolled/project "p" is not enrolled for cloud sync yet`; si no `ready/ready/upgrade_ready/project "p" is ready for cloud bootstrap`. Si hay mutaciones heredadas bloqueadas se sustituye por `blocked/blocked/upgrade_blocked_legacy_mutation_manual/manual-action-required: <primer mensaje> (seq=N entity=e op=o)`; si solo reparables, `blocked/repairable/upgrade_repairable_legacy_mutation_payload/project "p" has R repairable legacy mutation payload issue(s); run \`odin cloud upgrade repair --project p --apply\``. Guarda la etapa (`doctor_ready` si `ready`, si no `doctor_blocked`) y escribe `project: p`, `status:`, `class:`, `reason_code:`, `message:`.
- **repair**: `project:`, `class:`, `reason_code:`, `message:`, `applied: true|false`.
- **bootstrap**: sin servidor → `odin: cloud upgrade bootstrap requires configured cloud server`; URL inválida → `invalid cloud runtime server URL: …`. Captura la instantánea; hallazgos bloqueados → `legacy mutation payloads require manual action before bootstrap (seq=N entity=e op=o): <mensaje>`; reparables → `legacy mutation payloads require repair before bootstrap: run \`odin cloud upgrade repair --project p --apply\``. Avanza por etapas (inscribir → `bootstrap_enrolled`; exportar con `odin-cloud-upgrade` → `bootstrap_pushed`; importar y comprobar el estado → `bootstrap_verified`), cada una guardada, y reanuda desde la última; en `bootstrap_verified` es un no-op. Errores `bootstrap first push|verification pull|verification status: …` salen con la guía de recuperación de la nube. Escribe `project:`, `stage:`, `resumed: <true si no empezó en planned>`, `noop: <true si ya estaba verificado>`.
- **remirror**: requiere servidor como bootstrap; `remirrorProject` + exportación como `odin-cloud-remirror`; un fallo marca el destino y sale con `odin: cloud remirror: …`. Escribe `project:`, `chunks_exported:` y `mutations_exported:`.
- **status**: `project: p` y `stage:` (`planned` si no hay estado); con estado añade `class:`, `reason_code:`, `reason_message:`.
- **rollback**: sin estado → `odin: rollback requires existing upgrade checkpoint state`; no se puede (verificado o sin instantánea) → `rollback is unavailable post-bootstrap; use explicit disconnect/unenroll flows` (sin prefijo, código 1); si no escribe `project:` y `stage: rolled_back`.

## Atestación de origen (`src/store/prompt-source.js`, `src/cli/commands/cloud-attest.js`)

`previewPromptSource(store, syncId)` lee el `sync_id` exacto de `user_prompts` (`kind = 'live'`) y de `prompt_tombstones` (`'deleted'`); devuelve `{sessionId, sourceInboxId, project, syncId, kind}` solo si hay **exactamente una** fila y sus cuatro campos no están vacíos; si no, `null`.

`confirmPromptSourceAttestation(store, remoteTarget, preview, assertedOwner, remoteAttestationId)` lanza `PromptSourceConfirmationError` (`prompt source confirmation rejected`) si falta el destino, el dueño o el identificador positivo, si la vista previa está incompleta o su `kind` no es `live|deleted`, si lo observado ahora ya no coincide con ella, o si la sesión viva tiene un dueño no vacío distinto del afirmado. Con confirmación previa del mismo `(remote_target, sync_id)`: otro origen o dueño → rechazo; un identificador menor → rechazo; igual con el mismo `kind` → inocuo, con otro `kind` → rechazo; mayor → actualiza `kind` e identificador. Sin confirmación previa la inserta en `prompt_source_confirmations`. Todo en una transacción.

`odin cloud attest-prompt-source --sync-id <id> --owner-project <p>` (exactamente esas cuatro palabras, en ese orden): `--help|-h|help` imprime `usage: odin cloud attest-prompt-source --sync-id <exact-sync-id> --owner-project <asserted-owner>`; otra forma → ese uso en el error estándar y `odin: one exact sync ID and an asserted owner project are required`. Errores previos a pedir confirmación: `cloud runtime configuration unavailable`, `cloud server URL is required`, `invalid cloud server URL`, `cloud server URL credentials are not allowed`, `human bearer token required for remote dual-grant enforcement`, `cloud transport configuration rejected`, `local store unavailable: …`. Después imprime (sin salto de línea final en la pregunta):

```
Observed source: session="s" source_inbox="i" sync_id="id" prompt_project="p" kind="live"
Human-asserted owner: "dueño"
Send this exact tuple for remote attestation? Type yes or no: 
```

Lee una línea: `yes` continúa; `no` → `attestation declined; no remote call made`; otra → `invalid confirmation; type yes or no; no remote call made`. Llama a `MutationTransport.attestPromptSource` (error `remote attestation failed: …`), exige un identificador positivo (`remote attestation returned no positive ID; local confirmation not saved`), guarda la confirmación con la dirección del servidor como destino (si falla: `remote attestation succeeded (ID N), but local confirmation failed: …; do not assume local authorization`) y escribe `Remote attestation ID N confirmed locally for sync ID "id"`.
